## Critical Bugs & Technical Debt

### 🔴 **Production Risks**

1. **Secret Management**: `config.py` defaults `secret_key`, `jwt_secret`, `database_url` to `"change-me"` — no validation that production values are set. Container will start with insecure defaults.

2. **CORS Wildcard in Production**: `cors_origins = "*"` default; `is_production` only hides `/test-task` from OpenAPI, doesn't enforce strict CORS.

3. **No Rate Limiting**: Auth endpoints (`/register`, `/login`) have no throttling — vulnerable to credential stuffing/enumeration (though auth errors are unified).

4. **Celery Worker Not Deployed**: `docker-compose.yml` defines `worker` and `scheduler` services but **K8s manifests only deploy the API**. Background jobs will not run in production.

5. **Database URL Mismatch**: Config uses port `5434` (host-mapped), but K8s service uses internal port `5432`. Will fail in-cluster unless env overridden.

6. **Job Pipeline Disconnected**: `backend/jobs/` (sources, normalizer, dedup, repository) uses **different models** (`Job` with UUID) than main app (`JobPosting` with integer PK). **No integration layer exists**.

7. **Evaluation Engine Incomplete**: Phase 3C+ (scoring, LLM evaluation, recommendation) is **entirely missing** — only schemas and deterministic extraction (3A-3B) implemented.

### 🟡 **Technical Debt**

1. **Dual Job Model Architecture**: `backend/app/models/job.py` (SQLAlchemy, integer PK, pgvector) vs `backend/jobs/models.py` (Pydantic, UUID, SQLite repo). Creates confusion and duplication.

2. **Import Path Fragility**: Dockerfile requires `PYTHONPATH=/app:/app/backend` hack to resolve cross-package imports (`backend.evaluation` → `backend.jobs`). Indicates poor package structure.

3. **No API Versioning Strategy Beyond v1**: Router prefix hardcoded; no deprecation policy.

4. **Missing Observability**: No structured logging, metrics (Prometheus), or tracing (OpenTelemetry) despite `monitoring/` directory existing.

5. **Test Coverage Gaps**: 
   - No tests for `GreenhouseDiscoveryAgent` (requires Playwright/Chromium)
   - No integration tests for Celery tasks
   - No contract tests for evaluation schemas

6. **Frontend Non-Functional**: Only 2 files; no authentication flow, no job dashboard, no API integration.

## Strongest Components

1. **Authentication & Security Layer** (`backend/app/core/security.py`, `backend/app/api/deps.py`) — Well-designed, fail-closed, prevents enumeration, proper token typing.
2. **Service Layer Separation** — Clean boundary between HTTP (routers) and business logic (services).
3. **Evaluation Schemas (Phase 3A-3B)** — Excellent Pydantic models with disclosure policy, evidence references, deterministic extraction — **production-ready data contracts**.
4. **Test Architecture** — Well-organized unit/integration/pg-integration split; SQLite for speed, Postgres for fidelity.
5. **Documentation Honesty** — README explicitly separates implemented vs. roadmap; CHANGELOG tracks reality.

---

## Weakest Components

1. **AI/Automation Core** — The entire value proposition (discovery → matching → application) is **unimplemented**.
2. **Job Pipeline Integration** — Two parallel job systems that don't talk to each other.
3. **Frontend** — Non-existent beyond scaffold.
4. **Production Readiness** — No secrets management, no observability, no worker deployment, no rate limiting.
5. **Cross-Package Architecture** — `backend.jobs` and `backend.evaluation` are separate packages with duplicate models, requiring `PYTHONPATH` hacks.

## Prioritized Next-Step Roadmap

### 🚨 **Immediate (Week 1-2) — Production Hardening**
1. **Enforce production secrets**: Add startup validation that `secret_key`, `jwt_secret`, `database_url` ≠ defaults
2. **Fix CORS**: Require explicit `CORS_ORIGINS` in production; fail startup if wildcard
3. **Add rate limiting** to `/auth/*` endpoints (slowapi or middleware)
4. **Deploy Celery worker** in K8s (separate Deployment with same image, different CMD)
5. **Fix DB URL** for in-cluster connectivity (use Kubernetes service DNS)

### 🔧 **Short-term (Month 1) — Connect the Pipeline**
6. **Unify Job Models**: Merge `backend/jobs/models.py` into `backend/app/models/job.py` or create clear adapter layer
7. **Wire Discovery → Ingestion**: Create Celery task that runs `GreenhouseDiscoveryAgent` → normalizes → saves via `job_service.create_job`
8. **Implement Embedding Pipeline**: Add task to generate `embedding` (OpenAI/local) on job insert; add pgvector similarity search endpoint
9. **Complete Evaluation Engine (Phase 3C)**: Implement deterministic scoring against `JobRequirements` → `EvaluationResult`

### 🧠 **Medium-term (Month 2-3) — AI Value Delivery**
10. **Candidate KB Integration**: Link `User.profile_data` → load Candidate KB → feed into evaluation
11. **Resume/Cover Letter Generation**: Implement using candidate claims + job requirements (template + LLM)
12. **Application Tracking**: Build out `ApplicationStatus` transitions (Discovered → Matched → Approved → Applied)
13. **Frontend MVP**: Auth flow + job list + application dashboard

### 🏗️ **Long-term (Month 3+) — Production Platform**
14. **Observability**: Structured logging, Prometheus metrics, OpenTelemetry tracing
15. **K8s Hardening**: HPA, PodDisruptionBudgets, NetworkPolicies, sealed-secrets
16. **Multi-source Discovery**: Add Lever, Workday, API-based sources (Apify, etc.)
17. **Human-in-the-loop Approval**: Email/Slack notification before application submission

## Verdict

**This is a well-engineered backend foundation (Phases 1-3) with excellent documentation discipline, but the AI/automation product is <20% built.** The repository honestly discloses this in README, but the extensive `docs/03_AI/` specifications create an illusion of progress that doesn't exist in code.

**Recommendation**: Freeze documentation expansion. Focus entirely on **unifying the job pipeline** and **implementing Phase 3C evaluation engine** — the first actual AI component that delivers user value. Without this, the project remains a CRUD API with aspirations.
